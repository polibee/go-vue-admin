# 多语言设计

## 能力边界

后端不额外开发 i18n 系统，直接使用 Goravel 原生本地化能力。前端使用 Vue 生态的 vue-i18n 处理浏览器端 UI 文案，不开发自定义 i18n 引擎。

```text
Goravel Localization -> API、验证、后端错误和邮件
vue-i18n             -> Vue 菜单、页面、表单和组件文本
```

## 设计结论

第一阶段支持：

~~~text
zh-CN
en-US
~~~

默认语言为 zh-CN。

语言包必须先按语言分组，再按功能拆分：

~~~text
语言 -> 功能 -> 翻译文件
~~~

不采用：

~~~text
功能 -> 语言
~~~

这样翻译人员可以集中处理某一种语言，也可以直接比较同一语言下的所有功能文案。

## 前端目录结构

~~~text
admin/src/locales/
├── index.ts
├── registry.ts
├── types.ts
├── zh-CN/
│   ├── core.json
│   ├── users.json
│   ├── roles.json
│   ├── permissions.json
│   ├── settings.json
│   └── plugins/
│       ├── example-blog.json
│       └── example-payment.json
└── en-US/
    ├── core.json
    ├── users.json
    ├── roles.json
    ├── permissions.json
    ├── settings.json
    └── plugins/
        ├── example-blog.json
        └── example-payment.json
~~~

功能较大时可以继续拆目录：

~~~text
zh-CN/
└── users/
    ├── common.json
    ├── list.json
    └── form.json
~~~

但语言目录必须始终位于第一层。

## JSON 还是 TypeScript

翻译内容使用 JSON：

~~~json
{
  "title": "用户管理",
  "fields": {
    "username": "用户名",
    "email": "邮箱"
  },
  "actions": {
    "create": "新增用户"
  },
  "errors": {
    "email_exists": "邮箱已存在"
  }
}
~~~

选择 JSON 的原因：

- 翻译内容和程序逻辑分离；
- 翻译人员不需要修改 TypeScript；
- 不允许在语言包内执行代码；
- 更容易做 Key 对比和缺失检查；
- 更容易接入翻译平台；
- 插件可以携带自己的语言资源；
- 与 Goravel 的 JSON 本地化文件保持一致。

TypeScript 只用于：

~~~text
index.ts       i18n 实例创建
registry.ts    语言包注册和加载
types.ts       Locale、Message 和 Registry 类型
~~~

禁止在语言包中使用函数、条件表达式或业务逻辑。

## Key 命名

使用功能命名空间：

~~~text
core.actions.save
users.title
users.fields.email
roles.actions.assign
plugins.status.enabled
~~~

JSON 文件内部不重复顶层模块名：

~~~json
{
  "title": "用户管理",
  "fields": {
    "email": "邮箱"
  }
}
~~~

文件路径已经提供了模块边界：

~~~text
zh-CN/users.json -> users.*
en-US/users.json -> users.*
~~~

## 前端 vue-i18n 加载

~~~ts
vue-i18n 只负责创建 Vue 应用的语言实例和切换语言。语言包使用 JSON，加载器负责按语言加载功能文件。
~~~

注册流程：

~~~text
加载当前语言的 Core 文件
    ↓
加载当前语言的内置 Module 文件
    ↓
加载当前语言的已启用 Plugin 文件
    ↓
校验命名空间和 Key
    ↓
创建 i18n 实例
~~~

第一阶段只实现 Core 和内置 Module 的静态加载或按路由懒加载。不要开发自定义 Locale Registry；未来插件只需在安装/构建阶段向 vue-i18n 注册声明的语言包。

## 后端 Goravel 语言包

Goravel 原生支持按语言目录、按功能文件组织语言包。平台后端直接采用 Goravel 的语言加载和 fallback 配置，不再封装第二套后端语言服务：

~~~text
backend/lang/
├── zh-CN/
│   ├── core.json
│   ├── users.json
│   ├── roles.json
│   └── plugins/
└── en-US/
    ├── core.json
    ├── users.json
    ├── roles.json
    └── plugins/
~~~

实际接入时遵循项目使用的 Goravel locale 命名配置；目录结构保持“语言优先、功能拆分”。验证消息、API 错误、邮件和后端日志中的用户文案均使用 Goravel Localization。

后端 API 错误返回稳定错误码、翻译 Key 和参数：

~~~json
{
  "code": "USER_EMAIL_EXISTS",
  "message": "users.errors.email_exists",
  "params": {
    "field": "email"
  }
}
~~~

前端根据当前语言显示文本；非 Vue 客户端可以通过 Accept-Language 请求后端本地化消息。

## 插件语言包

插件包内部可以携带语言文件，但未来插件必须通过宿主提供的 Goravel Localization 和 vue-i18n 接入点加载，不能创建第三套翻译系统：

~~~text
plugin package/
└── locales/
    ├── zh-CN/
    │   └── example-blog.json
    └── en-US/
        └── example-blog.json
~~~

内置插件在项目中归档为：

~~~text
admin/src/locales/
├── zh-CN/plugins/example-blog.json
└── en-US/plugins/example-blog.json
~~~

插件只能注册自己的命名空间：

~~~text
example-blog.title
example-blog.fields.slug
example-blog.errors.publish_failed
~~~

插件不能覆盖：

~~~text
core.*
users.*
其他插件的命名空间
~~~

插件停用或卸载后，其语言包、菜单、权限和 Resource 注册必须一并失效。

## 语言选择优先级

~~~text
用户显式选择
    ↓
用户账户语言
    ↓
浏览器 Accept-Language
    ↓
系统默认 zh-CN
~~~

缺失 Key 时：

- 开发环境输出警告；
- 测试环境失败；
- 生产环境记录诊断信息；
- 不允许静默显示错误 Key。

## 验收

- zh-CN 和 en-US 功能文件结构一致；
- 两种语言的 Key 集合一致；
- 所有功能 Key 都有命名空间；
- 翻译内容只存在于 JSON；
- 页面不存在硬编码用户可见文案；
- 插件不能覆盖 Core、Module 或其他 Plugin 的 Key；
- 未启用插件的前端语言包不会进入运行时；
- 语言切换不会破坏路由、权限和 Resource 状态。
