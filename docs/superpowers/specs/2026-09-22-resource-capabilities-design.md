# Resource Capabilities Design

## 目标

在现有通用 Admin Resource 基础上，补齐生产级后台最重要的四类通用能力：数据范围权限、字段权限、Manifest 驱动的批量 Action，以及资源关系和复杂表单扩展点。

本设计以现有 Resource Registry、统一 CRUD API、ResourceSpec、RBAC 和生成器为基础，不建立第二套权限、路由、ORM、缓存或表单系统。

## 范围和边界

本阶段包含：

1. 后端统一数据范围契约，并应用到列表、详情、搜索、导出、新增、更新和删除。
2. ResourceSpec 字段级可见、可读、可写和敏感字段策略。
3. Manifest 声明式批量 Action 及统一 HTTP 契约。
4. 资源关系元数据、表单分组和基础联动扩展点。
5. OpenAPI、前端 Resource 页面、生成器、测试和示例资源同步升级。

本阶段不包含：

- 请求/响应完整审计和脱敏；
- 通用 CSV 导入；
- 插件安装、启停、卸载和运行时隔离；
- AI 生成业务规则；
- 自动执行数据库迁移；
- 自动向角色授予新权限；
- 审批、状态机、实时数据和复杂领域流程。

复杂业务应继续使用独立 Custom Page、Controller、Service 和 Repository，不把业务规则序列化到 Resource Manifest。

## 设计原则

- 后端是权限和数据裁剪的唯一可信边界，前端隐藏只是体验优化。
- ResourceSpec 是后端、前端、OpenAPI、生成器和测试的唯一契约来源。
- 默认行为保持向后兼容：未声明数据范围时使用 `all`，未声明字段限制时按现有公开字段处理。
- 生成器只修改生成专属 discovery 文件，人工维护的路由、Provider、Registry 和业务实现不被覆盖。
- 所有数据库变化只生成迁移文件，必须人工审阅、注册和执行。
- 每一阶段必须能独立测试、独立验收和独立回滚。

## 阶段一：通用数据范围权限

### 契约

在 Admin Core 中增加数据范围解析边界。资源查询在执行前获得当前用户上下文和资源范围，Repository 或统一查询适配器应用范围条件。

首期支持：

- `all`：访问资源的全部记录；
- `own`：只能访问当前用户拥有或创建的记录。

契约预留但首期不启用：

- `department`：按组织或部门字段过滤；
- `tenant`：按租户字段过滤。

`department` 和 `tenant` 必须在项目明确拥有对应领域模型后再实现，不在本阶段伪造字段或默认关系。

### 应用范围

相同的数据范围必须应用到：

- 列表和分页；
- 详情；
- 搜索和筛选；
- CSV 导出；
- 更新和删除；
- 批量 Action。

新增操作只校验允许写入的归属字段，不允许客户端通过请求体绕过范围规则。

### 验收标准

- 范围外详情、更新、删除和导出不会暴露数据；
- 搜索、排序、分页和统计结果不包含范围外记录；
- `all` 资源的现有行为不回归；
- `own` 资源有成功、越权和空结果测试；
- 资源权限和数据范围同时存在时必须全部满足。

## 阶段二：通用字段权限

### ResourceSpec 字段策略

字段元数据增加以下可选策略：

```text
visible   是否出现在资源契约和页面中
readable  当前用户是否可以读取字段值
writable  当前用户是否可以提交字段值
sensitive 是否属于敏感字段，默认不参与搜索和导出
```

字段策略可以由资源默认值和角色或权限上下文共同决定，但最终裁剪必须发生在后端响应和持久化之前。

### 行为

- `readable=false` 的字段不出现在列表、详情、搜索结果和导出中；
- `writable=false` 的字段提交时返回稳定的权限错误；
- `sensitive=true` 的字段默认不进入全局搜索、CSV 导出和普通审计 metadata；
- 前端根据资源契约隐藏列、输入项和详情项；
- 不能通过直接调用 API 或修改浏览器请求绕过字段策略。

### 验收标准

- 字段权限在列表、详情、导出和写入四条路径分别测试；
- 未授权字段不会因空值、排序或搜索参数泄露；
- 表单只提交允许写入的字段；
- 生成器能够为字段策略生成稳定的后端和前端产物。

## 阶段三：Manifest 驱动的批量 Action

### HTTP 契约

统一入口：

```text
POST /api/v1/admin/{resource}/actions/{action}
```

请求体：

```json
{
  "ids": [1, 2, 3],
  "payload": {}
}
```

Manifest Action 必须声明：

- action name；
- label；
- action kind；
- required permission；
- 是否允许批量；
- 输入 payload 的契约标识。

Manifest 只声明元数据，不携带可执行代码。实际行为由资源模块的显式 Go Action Handler 实现，并继续遵循 Controller、Service、Repository 分层。

### 执行规则

- 先校验资源和 Action 是否存在；
- 再校验 Action 权限；
- 再逐条应用数据范围和字段权限；
- 根据 Action 的事务策略执行；
- 返回成功、失败和跳过记录的稳定结构；
- 资源级失败不能静默当作成功。

现有用户状态批量操作迁移为该契约的业务 Action，但保留最后管理员保护等领域规则在 users Service 中实现。

### 验收标准

- 未声明 Action 不能被调用；
- 无 Action 权限返回权限错误；
- 范围外 ID 不被修改；
- 部分成功结果可被前端正确展示；
- users 状态批量操作和生成资源 Action 均通过接口测试。

## 阶段四：资源关系和复杂表单扩展点

### 关系元数据

首期只定义声明式关系描述，不自动推断数据库关系：

- `belongsTo`；
- `hasMany`；
- 关联资源名称；
- 展示字段；
- 可选过滤字段；
- 是否允许在表单中选择。

关系数据的查询和写入必须通过明确的资源或领域接口，不允许前端拼接任意表名和字段名。

### 表单扩展

ResourceSpec 可以声明：

- 表单分组；
- 详情区块；
- 字段布局；
- 基础字段依赖和联动条件。

需要审批、状态机、实时计算、跨聚合事务或复杂可视化的页面，不扩展通用 ResourceFormView，而是转入模块自己的 Custom Page。

### 验收标准

- 生成资源可以稳定渲染简单关系字段；
- 关系选择受到资源权限和数据范围约束；
- 关系字段不能绕过后端校验写入非法 ID；
- 简单分组和详情区块可由前端契约渲染；
- 复杂业务仍可通过 Custom Page 扩展，不影响通用资源页面。

## 生成器和契约同步

`admin:make-resource` 继续作为唯一主入口，统一从 ResourceSpec 派生：

- 后端 Resource Manifest；
- 数据范围和字段策略；
- 批量 Action 声明；
- 关系和表单元数据；
- OpenAPI Schema；
- 前端列表、表单和详情页面；
- 权限、菜单、测试和 README。

生成器不自动注册角色数据、不执行迁移、不覆盖人工业务实现。生成后的迁移仍需人工审核和执行。

## 验证策略

每个阶段至少包含：

1. Core 契约单元测试；
2. Controller/Service/Repository 边界测试；
3. OpenAPI 契约测试；
4. 前端类型检查和 Resource 页面测试；
5. Generator Golden File 测试；
6. 一个真实示例资源的 HTTP 端到端验收；
7. `go test ./... -count=1`、前端 `vue-tsc -b` 和生产构建。

数据库相关测试使用本地 Laragon PostgreSQL。生成器不得自动连接数据库或执行迁移；需要数据库验收时由人工审阅迁移后执行。

## 分阶段交付顺序

1. 阶段一：数据范围契约、`all/own` 实现和验收；
2. 阶段二：字段策略、响应裁剪和写入保护；
3. 阶段三：批量 Action 契约和 users 迁移；
4. 阶段四：关系元数据、表单扩展和生成器同步；
5. 每阶段完成后保留本地里程碑提交，全部阶段完成并通过集成验收后再统一推送 GitHub。
