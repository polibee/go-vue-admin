# Resource Generator Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Implement the first deterministic `admin:make-resource` generator slice that creates a reviewable backend Resource skeleton and migration without auto-registering runtime routes or executing migrations.

**Architecture:** Parse and validate command input into an immutable normalized `Spec`, render every output in memory through deterministic templates, then let a conflict-aware `Writer` commit the complete output set to disk. The command registers only the generator itself; generated routes, Registry entries, and migrations remain explicit developer actions.

**Tech Stack:** Go 1.27, Goravel v1.18 console contracts, `text/template`, `go/format`, standard-library filesystem APIs, Go `testing` package, golden fixtures.

**Spec:** `docs/superpowers/specs/2026-09-21-resource-generator-design.md`

## Global Constraints

- The command runs from the `backend/` project root as `go run . artisan admin:make-resource ...`.
- The command accepts a resource name and repeated `--field=name:type[:required]` options.
- Supported field types are `text`, `email`, `password`, `integer`, `boolean`, and `select`.
- The generator must be deterministic for identical input and preserve field input order.
- Existing files cause the complete command to fail before any output is written.
- Generated files contain `Code generated by admin:make-resource. DO NOT EDIT.`.
- The generator may create a new migration file but must never execute a migration or modify an existing migration.
- The generator must not auto-register routes, permissions, or Resource Registry entries.
- No third-party dependency or lockfile change is allowed.

## Review Focus

- Invalid resource names and Go identifier conversion: reject unsafe names before filesystem access; test names beginning with digits, containing underscores, and containing path separators.
- Duplicate or malformed fields: reject duplicate names, missing types, unknown types, and invalid `required` suffixes before writing.
- Partial-write safety: an existing target in the middle of the output set must leave every target absent after failure.
- Deterministic output: repeated renders with the same ordered fields must produce identical paths and bytes.
- Migration safety: generated migration content is written as a file only; tests must prove no migration runner or database call is invoked by the command.
